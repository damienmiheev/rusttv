## Milestone 1 — read-only CLI core

Small PRs, in order:

1. Workspace skeleton: `rusttv-core`, `rusttv-cli`, `rust-toolchain.toml`, `deny.toml`, CI (fmt, clippy, test, deny) on macOS + Linux.
2. `Adb` trait, `SystemAdb`, `FakeAdb`; typed `DeviceCommand` with `RiskClass`; test asserting every M1 command is R0.
3. `rusttv device list` and `rusttv device connect <addr>` (connect is a host-side action, not a device change).
4. `rusttv device inspect [--json]`: manufacturer, model, Android/API level, fingerprint, ABIs, RAM, storage, ADB capabilities probe. Parsers tested on fixtures captured from the emulator and the Philips TV.
5. `rusttv apps list [--json]` (system/third-party/disabled flags).
6. `rusttv performance snapshot [--json]`: memory + CPU summary, launcher process memory.
7. JSON envelope + error codes documented; `compat/` schema and the Philips TV profile generated from `inspect`.

**Progress (2026-10-23):** steps 1–7 done and tested on a real Pixel emulator capture (`crates/rusttv-core/src/fixtures/`). Remaining, all needing the Philips TV: its captures and profile, and the ADB capability probe (step 4).

**Done when:** all commands work against the emulator and the Philips TV, all checks green in CI, no device-modifying command exists in the codebase, and a newcomer can run `cargo run -p rusttv-cli -- device inspect` from the README.

## MVP success criteria (end of Phase 2)

Launcher:

- Builds an APK in CI for `arm64-v8a`, `armeabi-v7a`, `x86_64`.
- Installs alongside the stock launcher, which stays untouched unless the user opts in to Home takeover (SECURITY.md); takeover and restore verified on the Philips TV (2026-10-23: takeover with setupwraith disabled too, survived a reboot, restore brought the stock Home back; compat profile marked `takeover_tested`). `rusttv launcher uninstall` refuses until the takeover is restored (SECURITY.md § Home takeover rule 6). Restore without a journal: `launcher restore --from-profile` (2026-10-23, tested against fakes). (`adb install --pkg ai.rusttv.launcher` refusing an APK of another package was verified on the Google TV emulator, API 34, on 2026-10-23: `INSTALL_FAILED_INVALID_APK ... inconsistent with ai.rusttv.spike`; recheck on the Philips TV.)
- Shows every app the stock launcher shows (LEANBACK_LAUNCHER), with banners/icons.
- Every tile reachable by D-pad; DPAD_CENTER launches; Home returns to RustTV when it is the default.
- Works offline; survives a 24 h soak with zero crashes/ANRs on the Philips TV.
- Fully removable with a single uninstall.

Measurement:

- Benchmarks for RustTV vs stock vs CleanYourTV vs one Kotlin launcher on the Philips TV, with raw data in the repo.
- Any public performance claim is backed by those results and limited to the measured device.

CLI:

- Read-only commands from Milestone 1 plus Phase 3 commands, all with stable `--json`.

## Recommended first coding milestone

Start Milestone 1, PR 1–2: the workspace skeleton with CI and the typed, read-only `DeviceCommand` + `Adb` trait. It is pure Rust with no Android build tooling, so it is the best place to learn ownership, error handling, and testing, and it creates the safety boundary (no free-form shell) before any other code depends on it.

## Parked ideas

Decided "not for now"; raise again when the core launcher is done.

- **Content rows on Home (like a "top shelf": Continue watching, app
  recommendations)** — parked 2026-10-23. Findings:
  - Apps publish this data to Android's TV provider, but only apps signed by
    the device maker or installed on the system partition may read all of it
    (`ACCESS_ALL_EPG_DATA`; [Android docs](https://developer.android.com/training/tv/tif/channel),
    [AOSP](https://source.android.com/docs/devices/tv)).
  - On Google TV, many apps send Continue watching and recommendations to
    Google's servers instead, which only the stock launcher shows.
  - Possible partial route: the *Watch Next* and channel rows apps still
    publish locally, readable with a permission the user grants
    ([cleanyourtv#363](https://github.com/Gathin23/cleanyourtv/pull/363); one
    developer's findings, not documented behaviour).
  - First step when picked up: a read-only count, on the Philips, of how many
    Watch Next and channel rows the installed apps publish (no titles), to see
    whether there would be any content to show.

- **Customisable Home screen (themes) and later a theme market** — parked
  2026-10-23. Idea: describe the Home screen in a file so anyone can make and
  load their own look and behaviour. Discussion so far:
  - Not HTML/CSS: rendering it needs a WebView (a browser engine, 100+ MB and
    a slow start), which would undo RustTV's speed and memory advantage.
  - Level 1 (most of the value): a versioned theme file (JSON or TOML,
    `schema_version`) with typed, range-checked parameters and defaults —
    colours, fonts, corner radius, spacing, tile size/shape, columns/rows,
    hero on/off and size, glow strength, animation timings, sway, focus
    scale, background image or colour. Today these are hard-coded in
    `home.slint` and `ui.rs`, so this also cleans the code up.
  - Level 2: a few polished layout presets (e.g. grid, single row + hero,
    compact list) chosen by name in the theme.
  - Level 3, only if needed: full custom UI as `.slint` files loaded at run
    time with Slint's interpreter (no browser, but costs size and start time).
  - Shared themes are untrusted input: data only, never code, with size and
    decode limits on images, so a bad theme can at worst look ugly. Forks of
    the repo are different: they are their own app.
  - A market needs distribution, signing, moderation and trademark rules
    (Phase 7+); a first step would be loading a theme from a file or URL and
    seeing whether people share themes.
  - The default theme stays the polished, Apple TV-like one.

- **Privacy menu: choose packages by category, on the Mac and on the TV** —
  parked 2026-10-23. A normal app (RustTV included, even as Home) can't
  disable other apps; only the adb shell or system apps can. Options discussed:
  - A. Interactive menu in the CLI: tick packages by category, saved to the
    choices file, then the usual dry run, typed confirmation and journal.
    Small–medium effort; the engine already does the work.
  - B. Privacy page in RustTV: catalog packages by category with state,
    description and tested flag (read-only); pressing one opens Android's own
    app info page and its Disable/Enable button (often greyed out for system
    apps, and outside our journal). Also shows if a firmware update re-enabled
    something. Medium effort.
  - C. Real toggles on the TV via the TV's own wireless debugging (shell
    rights), restarted after each reboot with `WRITE_SECURE_SETTINGS`, plus a
    "Reboot TV" item. Possible (Shizuku does this on Android 13–14), but large
    effort and a big attack surface: the always-running Home would hold
    shell-level power. If ever done: through Shizuku and a separate tools app,
    never inside Home, with a written safety review and remote-confirmed
    approvals designed so nothing confirms by accident.
  - Leaning when picked up: A + B first; C only as its own decision.

- **Settings page with Screen care (OLED), and a top-right status corner** —
  parked 2026-10-23. Facts from the Philips 65OLED818 (read-only): Google TV's
  slideshow screensaver (`dreamx` Backdrop) is on after 10 min
  (`screen_off_timeout` 600000) and works over RustTV; TP Vision's
  `ImageStickingService` (GFX capture, in `org.droidtv.tvsystemui`) runs all
  the time and dims static areas of the whole picture. So RustTV's own care
  adds little on this TV, but should be configurable for others. Design
  discussed:
  - Settings in RustTV's app storage (typed values, safe defaults if broken;
    a first step towards the level 1 theme file above). Remote-friendly
    choices from fixed steps, no sliders.
  - Screen care: pixel shift on/off (default on: slow ±4 UI px every 3 min);
    dim when idle off / 1 / 2 / 5 min (default off on TVs that protect
    themselves); dim to 20 / 40 / 60 %; first press when dimmed only wakes or
    wakes and acts (owner leaned: 40 %, only wake). Shows the TV's own
    screensaver timeout read-only, flags a dim time later than it, and opens
    Android's screensaver settings (an app can't change them).
  - Entry point (owner's idea): a gear in the top-right corner, possibly with
    more status there — avatar, Wi-Fi status, notifications — to be discussed.
  - Must be a clean design aligned with the current home screen; use the
    `emil-design-eng` skill when designing it.

- **Button shortcuts and macros** — parked 2026-10-23; owner: maybe a brand
  new module, scope and actions still open. Discussion so far:
  - Scope is the key decision. On RustTV's home screen RustTV gets every key
    it is sent, with no permission. Shortcuts inside other apps (e.g. while
    Netflix plays) need an accessibility service, which can read every key
    press in every app: a large security and privacy step needing its own
    safety review. Home, the Assistant button and the Netflix/YouTube/Prime
    buttons are handled by the TV before any app and can't be remapped.
  - Triggers: a key plus short / long / double press (numbers, colour keys,
    media keys, CH+/−, Info/Options if the TV passes them); OK, Back and the
    arrows stay reserved for navigation.
  - Actions from a fixed, typed list (never code): open an app, reopen the
    last app, switch HDMI input (if Philips allows an app to), volume/mute,
    open an Android settings page, RustTV actions (hide/move, hidden apps,
    T9). Macros: a short sequence with waits (e.g. up to 8 steps, no loops);
    they can't press keys inside other apps.
  - Set up on the TV: "press the button you want to use", choose the action.
  - Conflicts (owner): before assigning, check what each button already does —
    RustTV's own navigation and menu keys, keys the TV or Google TV handle
    themselves (Home, Assistant, app buttons, possibly Info/Options/colour keys
    on Philips), and other shortcuts — and warn or refuse. First step when
    picked up: a read-only check on the Philips of which keys reach an app
    and which the system consumes.
  - Depends on the Settings page above.

- **Volume on the phone: level, slider and mute** — parked 2026-10-27
  (owner idea). Tapping a volume button on the phone opens a volume slider
  showing the TV's current level (0–60 on the Philips), and drags set it
  directly; a mute button next to it. Notes so far:
  - The level is readable and settable through the audio service from the
    pointer's service, which already changes volume (and shows the TV's own
    volume bar); a slider would send a target level, not many steps.
  - Mute: `ADJUST_TOGGLE_MUTE` (already wired as the phone's `mute` key, not
    yet on the page); the phone would show muted / unmuted from the TV's
    state.
  - Phone layout: the deck stays one line; the slider opens over the
    touchpad and closes by itself after a few seconds.

- **Skip intro / skip ad from the phone** — parked 2026-10-27 (owner idea).
  A "Skip" button on the phone that lights up when the app in front shows
  its own skip button, and presses it. Notes so far:
  - Only skips the app offers: RustTV finds the button by its name through
    the pointer's service (as Done finds a search button) and clicks it. It
    never skips what has no skip button and never blocks ads (app rules,
    accounts).
  - Works where apps expose their buttons (web players in the browsers,
    Kyivstar TV in the 2026-10-26 tests); not in apps that draw everything
    themselves (YouTube, Netflix, Megogo showed almost no elements). In
    YouTube the skip button takes focus, so the phone's OK usually skips.
  - Needs the names in the launcher's languages ("Skip intro", "Пропустити
    заставку", …), like the search-button words.

- **Paste from the phone's clipboard** — parked 2026-10-27 (owner idea). One
  tap puts the phone's clipboard (a link, a password) into the TV's focused
  text field. Notes so far:
  - The page reads the clipboard with the browser's clipboard API, only
    after a tap and only over HTTPS; iOS asks "Paste?" each time. The text
    goes through the existing encrypted typing path (set-text on the
    field), so it works in fields RustTV can already type into.
  - Never stored on the TV or logged; password fields stay masked.

- **Open a link on the TV** — parked 2026-10-27 (owner idea). Send a link
  from the phone (YouTube video, article, stream) and it opens on the TV in
  the right app. Notes so far:
  - The phone's share menu can list RustTV Remote only for an installed web
    app with a share target (Chrome on Android); iOS has no share target for
    web apps, so there it's paste-a-link on the page (or the clipboard idea
    above).
  - The TV opens it with a typed intent: known hosts to their apps
    (YouTube links to YouTube, like the search address), others to the TV's
    browser; only http(s) links, checked like other phone input.

- **Phone remote and second screen** — **planned 2026-10-25 as RustTV
  Remote, see REMOTE.md** (0.3.0). The owner's decisions there replace the
  discussion that was here; per-app second-screen views remain research
  (REMOTE.md § 7, phase 4).

- **Tweaks + History: TV-side changes with a git-backed history** — **built
  2026-10-24, see HISTORY.md** (the discussion below is kept as its origin).
  Parked 2026-10-24. Owner's idea: what the CLI can change, the launcher's Settings
  page can change too, and every change from either side is a snapshot in a
  history the Mac can review and restore. Discussion so far:
  - **History lives on the TV** (source of truth), with a copy on the Mac.
    Each entry: time, who (Mac CLI / TV page / drift), message, previous
    hash, full snapshot. A lost Mac no longer means lost journals. Changes
    made outside RustTV (vendor Settings, firmware updates) appear as
    "drift" entries, which also gives the firmware-update guard.
  - **One state file with sections** (`schema_version`, `[launcher]`,
    `[settings.global]`, `[packages]`): one atomic rename keeps every
    snapshot consistent; diffs stay readable per section. Large or separate
    user content (phone remote layouts, themes, add-on settings) gets its own
    files.
  - **Git as the store:** commits = snapshots, `main` = what is really on
    the TV and verified. Editing on the TV is a `draft` branch; Save turns
    the diff `main → draft` into a normal plan (approval, apply, verify) and
    merges only after verification; Cancel deletes the branch; a failed apply
    rolls back and keeps the draft. Drift during editing moves `main` first
    and the draft is rebased and re-planned. Git only stores and compares;
    the safety engine still makes every change.
  - **Real git vs git-like:** real git (gitoxide, pure Rust) gives branches,
    merges, rebase and bundles (`git bundle` → the CLI copies it through an
    adb-shell-only read door → `git fetch` on the Mac) and every git tool;
    a hand-written hash-chained log is smaller but rebuilds all that. First
    step when picked up: a spike measuring a minimal gitoxide build in the
    armv7 APK (size, memory); real git if small, else a git-like log on the
    TV exported to a real git repo on the Mac.
  - **What the TV may change:** global/secure settings (e.g. animation
    scales) after a one-time `WRITE_SECURE_SETTINGS` grant made from the Mac
    through a plan with approval (survives reboots). Disabling packages needs
    shell rights: stays on the Mac; the TV page shows state and queues such
    changes on a `pending-mac` branch, applied with typed approval the next
    time the CLI connects.
  - **Approval on the TV:** no terminal there, so a deliberate gesture
    (e.g. a confirm screen listing exactly what changes, hold OK for 2 s)
    that a stray press or an agent can't trigger. Changes the safety rules:
    needs a dated owner decision in SECURITY.md.
  - **What the history enables:** time machine (browse and restore any
    snapshot, always as a plan); copy-paste a snapshot to another TV (covers
    "move to a new TV" and several TVs from one Mac); diff two TVs; tags
    ("known good"); bisect to find the change that broke something; profiles
    (kids, guest) and scheduled switches (bedtime) as branches; shareable
    presets without personal data, feeding a community compat database.
  - **Privacy:** the history contains the TV's app list, so it lives in the
    owner's private RustTV data folder, never in this repository and never
    pushed anywhere unless the owner chooses to.
  - Depends on the Settings page above; pairs with the change timeline
    ("undo anything") idea.

- **Split screen and picture-in-picture (experimental)** — parked 2026-10-24.
  Owner's idea: open an app on half the screen (a match plus stats, a game
  on HDMI plus a guide, a cooking video plus the recipe). Ranked below the
  phone remote and Tweaks + History: feasibility unknown, smaller everyday
  value. Discussion so far:
  - **Picture-in-picture** is built into Android TV, but each app decides
    whether it supports it; the launcher can't force it. RustTV could list
    the installed apps that declare PiP and offer "continue in a corner" for
    them.
  - **Two apps side by side:** Android has split screen and free-form
    windows, but TV makers usually switch them off. The developer switches
    `enable_freeform_support` and `force_resizable_activities` (global
    settings) might turn them on, set through the safety engine like the
    animation scales (plan, approval, restore); then the launcher opens two
    apps with launch bounds for each half. Unknowns: whether the Philips
    honours the switches; whether its chip can decode two video streams;
    apps designed for full screen may look broken at half size; the remote
    controls one half at a time (needs a focus-switch button and a visible
    border); some apps pause when not focused.
  - **HDMI next to an app** depends on the TV's own hardware (some Philips
    models had a "multi view"); an app can't build it.
  - **First step when picked up:** a read-only check on the Philips of what
    it reports about multi-window and PiP support and which installed apps
    declare PiP; if promising, a reversible test of the two switches with
    the owner's approval, judged by eye.

- **Panels: add-ons with several faces, and a theme builder** — parked
  2026-10-24. Owner's idea: features such as History/Settings become add-ons
  ("panels" for people, "add-ons" in code; "widgets" clashes with Android's
  App Widgets; "cards" and "modules" also considered) kept in the RustTV
  folder on the launcher, each implementing one contract with several views,
  like iOS widgets. Later: easy new add-ons, maybe a marketplace, and a tool
  for building themes (grids, buttons, menus, panels inside menus). Discussion
  so far:
  - **Faces, one contract:** *page* (full screen, as Settings is now);
    *tile* on the Home grid in fixed sizes (1×1, wide 2×1, maybe 2×2: a
    weather add-on shows a temperature small and a forecast wide); *row*
    (a compact line in a menu or the Settings list: "History: 3 changes
    today", a toggle). Possible later faces: *ambient* (idle or screensaver
    overlay), the *hero* area above the grid, and a *phone* face for the
    phone remote (the add-on brings its own phone layout). Each face gets
    data in and a fixed list of actions out (open, toggle, request a change
    through the existing review + code + hold screen); none touches the
    system directly. Tiles render only while visible, with no per-frame work
    (the launcher's performance budgets apply to every add-on).
  - **Trust levels — the hard part is other people's code, not the views:**
    1. *Built-in panels*, compiled in (History, Settings, later Weather):
       fast and safe; today's model.
    2. *Data-only panels*: layouts, themes, phone-remote layouts, presets.
       No code, so nothing harmful; can be shared or sold from day one.
    3. *Code panels from others*, sandboxed: a WASM interpreter with a
       capability API, or a separate app talking through a content provider
       like the history door. Running someone's code inside Home is the
       biggest risk RustTV could take on: needs its own safety review and a
       dated owner decision (SECURITY.md) before any work.
  - **Theme builder:** a theme is data — the grid (which panels where, their
    sizes), the tokens the `Theme` global already has (colours, type sizes,
    radius, motion), the menus and the panels inside them. Edited on the Mac
    (later from the phone), previewed in the desktop mode, applied through
    review and confirm; every change lands in History, so "undo my theme"
    and "copy my setup to another TV" come for free.
  - **Marketplace:** first for data-only panels and themes (safe); code
    panels only after level 3 has a sandbox. Distribution, signing and
    updates would follow the launcher's update rules (signed, checked,
    confirmed by the person).
  - **Groundwork already there:** the Settings page is a section list plus a
    panel; each section can later become an add-on's page face, so turning
    History into the first add-on is a refactor, not a rewrite. No add-on
    abstraction is built before the idea is picked up (no speculative code).
  - **Open questions:** the name; the face list and tile sizes; the sandbox
    choice (WASM interpreter size and speed on armv7 to be measured); how a
    panel declares the data it needs; the marketplace's trust and payment
    model; where add-ons live in the repository (crates named
    `rusttv-<name>`, e.g. `rusttv-weather`).
  - **First step when picked up:** write the contract for the built-in
    panels only (page, tile, row), move History/Settings onto it, and
    measure that Home's start, resume and frame times don't change.
