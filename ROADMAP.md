## Milestone 1 — read-only CLI core

Small PRs, in order:

1. Workspace skeleton: `rusttv-core`, `rusttv-cli`, `rust-toolchain.toml`, `deny.toml`, CI (fmt, clippy, test, deny) on macOS + Linux.
2. `Adb` trait, `SystemAdb`, `FakeAdb`; typed `DeviceCommand` with `RiskClass`; test asserting every M1 command is R0.
3. `rusttv device list` and `rusttv device connect <addr>` (connect is a host-side action, not a device change).
4. `rusttv device inspect [--json]`: manufacturer, model, Android/API level, fingerprint, ABIs, RAM, storage, ADB capabilities probe. Parsers tested on fixtures captured from the emulator and the Philips TV.
5. `rusttv apps list [--json]` (system/third-party/disabled flags).
6. `rusttv performance snapshot [--json]`: memory + CPU summary, launcher process memory.
7. JSON envelope + error codes documented; `compat/` schema and the Philips TV profile generated from `inspect`.

**Progress (2026-10-23):** steps 1–7 done and tested on a real Pixel emulator capture (`crates/rusttv-core/src/fixtures/`). Remaining, all needing the Philips TV: its captures and profile, and the ADB capability probe (step 4).

**Done when:** all commands work against the emulator and the Philips TV, all checks green in CI, no device-modifying command exists in the codebase, and a newcomer can run `cargo run -p rusttv-cli -- device inspect` from the README.

## MVP success criteria (end of Phase 2)

Launcher:

- Builds an APK in CI for `arm64-v8a`, `armeabi-v7a`, `x86_64`.
- Installs alongside the stock launcher, which stays untouched unless the user opts in to Home takeover (SECURITY.md); takeover and restore verified on the Philips TV (2026-10-23: takeover with setupwraith disabled too, survived a reboot, restore brought the stock Home back; compat profile marked `takeover_tested`). `rusttv launcher uninstall` refuses until the takeover is restored (SECURITY.md § Home takeover rule 6). Restore without a journal: `launcher restore --from-profile` (2026-10-23, tested against fakes). (`adb install --pkg ai.rusttv.launcher` refusing an APK of another package was verified on the Google TV emulator, API 34, on 2026-10-23: `INSTALL_FAILED_INVALID_APK ... inconsistent with ai.rusttv.spike`; recheck on the Philips TV.)
- Shows every app the stock launcher shows (LEANBACK_LAUNCHER), with banners/icons.
- Every tile reachable by D-pad; DPAD_CENTER launches; Home returns to RustTV when it is the default.
- Works offline; survives a 24 h soak with zero crashes/ANRs on the Philips TV.
- Fully removable with a single uninstall.

Measurement:

- Benchmarks for RustTV vs stock vs CleanYourTV vs one Kotlin launcher on the Philips TV, with raw data in the repo.
- Any public performance claim is backed by those results and limited to the measured device.

CLI:

- Read-only commands from Milestone 1 plus Phase 3 commands, all with stable `--json`.

## Recommended first coding milestone

Start Milestone 1, PR 1–2: the workspace skeleton with CI and the typed, read-only `DeviceCommand` + `Adb` trait. It is pure Rust with no Android build tooling, so it is the best place to learn ownership, error handling, and testing, and it creates the safety boundary (no free-form shell) before any other code depends on it.

## Parked ideas

Decided "not for now"; raise again when the core launcher is done.

- **Content rows on Home (like a "top shelf": Continue watching, app
  recommendations)** — parked 2026-10-23. Findings:
  - Apps publish this data to Android's TV provider, but only apps signed by
    the device maker or installed on the system partition may read all of it
    (`ACCESS_ALL_EPG_DATA`; [Android docs](https://developer.android.com/training/tv/tif/channel),
    [AOSP](https://source.android.com/docs/devices/tv)).
  - On Google TV, many apps send Continue watching and recommendations to
    Google's servers instead, which only the stock launcher shows.
  - Possible partial route: the *Watch Next* and channel rows apps still
    publish locally, readable with a permission the user grants
    ([cleanyourtv#363](https://github.com/Gathin23/cleanyourtv/pull/363); one
    developer's findings, not documented behaviour).
  - First step when picked up: a read-only count, on the Philips, of how many
    Watch Next and channel rows the installed apps publish (no titles), to see
    whether there would be any content to show.

- **Customisable Home screen (themes) and later a theme market** — parked
  2026-10-23. Idea: describe the Home screen in a file so anyone can make and
  load their own look and behaviour. Discussion so far:
  - Not HTML/CSS: rendering it needs a WebView (a browser engine, 100+ MB and
    a slow start), which would undo RustTV's speed and memory advantage.
  - Level 1 (most of the value): a versioned theme file (JSON or TOML,
    `schema_version`) with typed, range-checked parameters and defaults —
    colours, fonts, corner radius, spacing, tile size/shape, columns/rows,
    hero on/off and size, glow strength, animation timings, sway, focus
    scale, background image or colour. Today these are hard-coded in
    `home.slint` and `ui.rs`, so this also cleans the code up.
  - Level 2: a few polished layout presets (e.g. grid, single row + hero,
    compact list) chosen by name in the theme.
  - Level 3, only if needed: full custom UI as `.slint` files loaded at run
    time with Slint's interpreter (no browser, but costs size and start time).
  - Shared themes are untrusted input: data only, never code, with size and
    decode limits on images, so a bad theme can at worst look ugly. Forks of
    the repo are different: they are their own app.
  - A market needs distribution, signing, moderation and trademark rules
    (Phase 7+); a first step would be loading a theme from a file or URL and
    seeing whether people share themes.
  - The default theme stays the polished, Apple TV-like one.

- **Background follows the focused app (drives Ambilight)** — parked
  2026-10-23. Ambilight in video mode already follows the colours near the
  screen edges, so no Philips API is needed: the Home background itself carries
  the focused app's colour. Options discussed, best first:
  - A heavily blurred, darkened copy of the focused app's banner as the whole
    background (a tiny cached image, e.g. 32×18, stretched with smoothing),
    so there is no visible border or frame.
  - A slight hue tint of the whole dark background.
  - A large, faint halo from the focused tile (weakest effect on Ambilight).
  - Open question: how strongly Ambilight reacts to dark colours. First step
    when picked up: a test build with 2–3 brightness levels, judged by eye on
    the TV (screencap is blocked on the Philips).

- **Privacy menu: choose packages by category, on the Mac and on the TV** —
  parked 2026-10-23. A normal app (RustTV included, even as Home) can't
  disable other apps; only the adb shell or system apps can. Options discussed:
  - A. Interactive menu in the CLI: tick packages by category, saved to the
    choices file, then the usual dry run, typed confirmation and journal.
    Small–medium effort; the engine already does the work.
  - B. Privacy page in RustTV: catalog packages by category with state,
    description and tested flag (read-only); pressing one opens Android's own
    app info page and its Disable/Enable button (often greyed out for system
    apps, and outside our journal). Also shows if a firmware update re-enabled
    something. Medium effort.
  - C. Real toggles on the TV via the TV's own wireless debugging (shell
    rights), restarted after each reboot with `WRITE_SECURE_SETTINGS`, plus a
    "Reboot TV" item. Possible (Shizuku does this on Android 13–14), but large
    effort and a big attack surface: the always-running Home would hold
    shell-level power. If ever done: through Shizuku and a separate tools app,
    never inside Home, with a written safety review and remote-confirmed
    approvals designed so nothing confirms by accident.
  - Leaning when picked up: A + B first; C only as its own decision.

- **Settings page with Screen care (OLED), and a top-right status corner** —
  parked 2026-10-23. Facts from the Philips 65OLED818 (read-only): Google TV's
  slideshow screensaver (`dreamx` Backdrop) is on after 10 min
  (`screen_off_timeout` 600000) and works over RustTV; TP Vision's
  `ImageStickingService` (GFX capture, in `org.droidtv.tvsystemui`) runs all
  the time and dims static areas of the whole picture. So RustTV's own care
  adds little on this TV, but should be configurable for others. Design
  discussed:
  - Settings in RustTV's app storage (typed values, safe defaults if broken;
    a first step towards the level 1 theme file above). Remote-friendly
    choices from fixed steps, no sliders.
  - Screen care: pixel shift on/off (default on: slow ±4 UI px every 3 min);
    dim when idle off / 1 / 2 / 5 min (default off on TVs that protect
    themselves); dim to 20 / 40 / 60 %; first press when dimmed only wakes or
    wakes and acts (owner leaned: 40 %, only wake). Shows the TV's own
    screensaver timeout read-only, flags a dim time later than it, and opens
    Android's screensaver settings (an app can't change them).
  - Entry point (owner's idea): a gear in the top-right corner, possibly with
    more status there — avatar, Wi-Fi status, notifications — to be discussed.
  - Must be a clean design aligned with the current home screen; use the
    `emil-design-eng` skill when designing it.

- **Button shortcuts and macros** — parked 2026-10-23; owner: maybe a brand
  new module, scope and actions still open. Discussion so far:
  - Scope is the key decision. On RustTV's home screen RustTV gets every key
    it is sent, with no permission. Shortcuts inside other apps (e.g. while
    Netflix plays) need an accessibility service, which can read every key
    press in every app: a large security and privacy step needing its own
    safety review. Home, the Assistant button and the Netflix/YouTube/Prime
    buttons are handled by the TV before any app and can't be remapped.
  - Triggers: a key plus short / long / double press (numbers, colour keys,
    media keys, CH+/−, Info/Options if the TV passes them); OK, Back and the
    arrows stay reserved for navigation.
  - Actions from a fixed, typed list (never code): open an app, reopen the
    last app, switch HDMI input (if Philips allows an app to), volume/mute,
    open an Android settings page, RustTV actions (hide/move, hidden apps,
    T9). Macros: a short sequence with waits (e.g. up to 8 steps, no loops);
    they can't press keys inside other apps.
  - Set up on the TV: "press the button you want to use", choose the action.
  - Conflicts (owner): before assigning, check what each button already does —
    RustTV's own navigation and menu keys, keys the TV or Google TV handle
    themselves (Home, Assistant, app buttons, possibly Info/Options/colour keys
    on Philips), and other shortcuts — and warn or refuse. First step when
    picked up: a read-only check on the Philips of which keys reach an app
    and which the system consumes.
  - Depends on the Settings page above.
