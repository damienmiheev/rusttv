# Security and Device Safety

## Reporting vulnerabilities

Until a dedicated address exists, report privately via GitHub Security Advisories on this repository. Do not open public issues for vulnerabilities.

## Absolute restrictions

RustTV never:

- uses root, flashes firmware, unlocks bootloaders, or modifies system partitions;
- uninstalls the stock launcher, or disables it outside the opt-in [Home takeover](#home-takeover-opt-in) flow;
- removes packages, except its own launcher (`ai.rusttv.launcher`) through `rusttv launcher uninstall`; the uninstall command takes no package name, so it can remove nothing else;
- executes free-form shell strings — device access only through typed `DeviceCommand`s;
- writes anything through the launcher's history door from MCP, or without a plan-applying command around it (risk class RL below);
- lets an AI agent apply a change without a human approving the specific plan, or (owner decision 2026-10-24) a time-limited delegation a human granted at a terminal for one device and the launcher plans only ([Delegated approval](#delegated-approval)), or (owner decision 2026-10-24) an approval a person made on the TV with the code only the screen shows ([Approval on the TV](#approval-on-the-tv));
- sends data off the user's machine (no telemetry). The launcher's update check ([Launcher updates](#launcher-updates)) only downloads from GitHub; it sends nothing but the requests themselves.

## Risk classes

Every `DeviceCommand` declares one:

| Class | Meaning | Examples | Who may run it |
|---|---|---|---|
| R0 Read | No state change | `getprop`, `pm list packages`, `dumpsys meminfo` | CLI, MCP freely |
| RL Launcher-private | Appends to RustTV's own history on the TV through the launcher's door; no device state changes | `adb exec-in content write --uri content://ai.rusttv.launcher.history/inbox/<nonce>`, `adb shell content call … --method commit --arg <kind>:<nonce>` | CLI only, around plan-applying commands and in `history restore-tv`; never MCP |
| R1 Transient | Changes runtime state only; reboot or app restart undoes it | `am start`, `am force-stop`, `input keyevent` | CLI; MCP for allowlisted targets |
| R2 Setting | Persistent, trivially reversible setting | `settings put global animator_duration_scale 0.5`, set default home | Only via an approved plan |
| R3 Package state | Enable/disable an app for user 0; install, upgrade or uninstall the RustTV launcher (its own package only) | `pm disable-user --user 0`, `adb install --pkg ai.rusttv.launcher <apk>` | Only via an approved plan; disabling: Phase 4+, known-device profile only |
| R4 Forbidden | Not implementable | uninstalling anything but RustTV's launcher, stock-launcher changes outside Home takeover, system partition writes | Nobody |

So far: R0 commands, two R1 commands for benchmarking (`am force-stop`, `am start`), one R2 command used only by optimizer profiles and `history restore` (`settings put global <key> <value>`, or `settings delete global <key>` to put back an unset key), limited to three allowlisted keys (`window_animation_scale`, `transition_animation_scale`, `animator_duration_scale`; a `SettingKey` enum, no free-form key or namespace) and values matching `[0-9]{1,2}(\.[0-9]{1,3})?`, two R3 commands used only by Home takeover, privacy profiles and `history restore` (`pm disable-user --user 0`, `pm enable --user 0`), two R2 commands used only by `history allow-tv-settings` / `revoke-tv-settings`, fixed to the launcher and one permission (`pm grant|revoke ai.rusttv.launcher android.permission.WRITE_SECURE_SETTINGS`), two RL commands for the history door (below), and three R3 commands used only by `launcher install`/`uninstall`, fixed to package `ai.rusttv.launcher` (`adb install --pkg ai.rusttv.launcher <apk>`, `adb install -r --pkg ...`, `pm uninstall ai.rusttv.launcher`), all run only through the safety engine (`rusttv-core` `plan` module). A unit test fails if anything else above R0 appears. Every R2/R3 command must have an inverse, except upgrading and uninstalling RustTV's own launcher, which can't be undone without the previous APK: plans accept those only as their last step, show "no undo", and a failure after them is reported as a failed rollback with the manual fix. `adb install` runs on the host, not through `adb shell`; its only free argument is a validated absolute APK path whose file name is limited to `[A-Za-z0-9._-]+.apk`, because older adb versions pass the file name to `pm` on the device.

*RL, owner decision 2026-10-24 (HISTORY.md § 5).* The one exception to "every modifying operation is a plan": the history door's two writes, which only append observations and notes to RustTV's own history on the TV (its private storage), claim a pending approval, or import into an empty history, and change no setting, package or app. They are ordered between R0 and R1 (above R0, so MCP never runs them; at most transient, so they need no inverse), fixed URIs with a validated 16-hex nonce, the payload on stdin. Plan-applying commands send them without an approval of their own, like the CLI's own journal writes; a failure is a warning. Putting a whole history back (`rusttv history restore-tv`) is still a plan with typed approval `history` whose two steps are RL. The journal records the payload's SHA-256 and size, not its bytes.

## The history door

*HISTORY.md § 5–7.* The launcher's `ContentProvider` `ai.rusttv.launcher.history` answers only callers with uid 2000, the adb shell. **uid 2000 is anything with adb on this TV**: this computer, wireless-debugging peers, Shizuku-style servers. They can already change packages; through the door they can only add observations and notes (labelled as such and separately capped, 30 an hour), claim a pending approval, or import into an empty history. They can't change the launcher's state, create or approve anything, or rewrite history; a forged observation shows as a `drift` entry from "your computer", and restoring to it from the TV needs the code and shows what it changes. Everything the TV sends is untrusted input to the CLI: exports are git packs checked object by object (ids recomputed, the chain from this computer's newest entry, one `state.toml` per entry, size limits) before this computer's copy moves; pending lists are checked against their SHA-256s.

*Pending approvals* (§ 6.3). Changes a person approved on the TV that the launcher can't make itself (packages; settings without the grant) wait as a pending approval for 2 h of TV uptime in the same boot. Only `rusttv history apply-pending` applies them, only at an interactive terminal (never `sync`, scripts, delegations or MCP), and never from a debuggable or profileable launcher (`dumpsys package` flags; `PENDING_REFUSED`). It first claims the approval through the door (the TV allows that once, so it can't be applied twice), then plans `history-restore` live with the same checks as `history restore` (protected rules 1–3 live, rule 4 without `--allow-untested`, never takeover packages), and applies it without typing only if the steps are exactly the approved changes with the same old values; otherwise it shows both and asks for the typed confirmation. Journals record `approved_by = { by = "tv", approval = "<sha256>" }`; a note may claim a TV approval only for an approval it consumed.

*`WRITE_SECURE_SETTINGS`* (§ 7). `rusttv history allow-tv-settings` grants it to the launcher in a plan (one R2 step, `pm grant ai.rusttv.launcher android.permission.WRITE_SECURE_SETTINGS`, verified with `dumpsys package`, undone by `pm revoke`; typed approval `allow`); `revoke-tv-settings` takes it back (`revoke`). The launcher writes only the three animation scales with it, through one function, after the code and hold OK on the TV. Each `history sync` reads a watchlist with R0 commands, `secure enabled_accessibility_services`, `secure default_input_method`, `global adb_wifi_enabled`, `secure install_non_market_apps`, `global package_verifier_enable`, `global http_proxy`, `global private_dns_specifier` and the grant itself (a fixed enum, no free-form key), compares it with the baseline kept on this computer (`<state dir>/history/<history id>.watchlist.toml`, never read back from the TV) and warns about each change.

*Tests only.* Debug builds with the `test-util` feature (the CLI's integration tests) treat stdin as a terminal when `RUSTTV_TEST_TERMINAL=1`, so the tests can type confirmations through a pipe; release builds have no such code, as with the test signing key (§ Updates).

## Protected package policy

A package is protected (no R3 action) if **any** of these is true:

1. It resolves `HOME`, or is the current/previous default home.
2. It provides an input method, accessibility service, TV input (HDMI/tuner), setup wizard, system UI, settings, package installer, network stack, Bluetooth/remote pairing, or Google Play services.
3. It is on the static deny-list in `compat/protected.toml`.
4. The device has no profile marking the package as tested-safe for that model **and** firmware family.

Rules 1–2 are computed live on the device each time, not cached. Unknown devices get R0–R1 only.

*As built (privacy profiles, OPTIMIZER.md § Generic design):* candidates come only from the compiled-in package catalog (`compat/packages/`; a test keeps it off `compat/protected.toml`) as selected by the person's local choices file, plus the choices file's `extra` packages. Before planning, `rusttv optimize apply privacy` reads, with R0 commands only:

- rule 1: the Home resolver and every Home candidate (`cmd package resolve-activity` / `query-activities ... HOME`);
- rule 2: every input method, enabled or not (`ime list -a -s`), and the enabled accessibility services (`settings get secure enabled_accessibility_services`). Output it can't read refuses the plan (`PRECONDITION_FAILED`), so a misread never passes;
- rule 3: `compat/protected.toml`, compiled into the binary (a copy on disk changes nothing; if it doesn't parse, every package counts as protected). It names by package what can't be detected live: TV inputs (any name containing `tvinput`, `com.android.providers.tv`, `com.mediatek.tv.service`, `org.droidtv`), the setup wizard, system UI, Settings, the settings provider, the adb shell, package installers, the network stack, Bluetooth, Google Play services and Store, the Assistant, keyboards, the stock launchers and RustTV's own launcher;
- rule 4: a package counts as tested-safe only if the device's bundled compat profile matches its model and firmware family and lists it under `[[privacy.tested]]`. Untested packages are left out of the plan, and with none tested left it is refused (`PROFILE_NOT_TESTED`). *Owner decision 2026-10-23:* a person may override rule 4, never rules 1–3, for one plan with `--allow-untested` (MCP: `allow_untested`, which only adds the flag to the command the person runs). The dry run then marks each such package "UNTESTED on this model" with what the catalog says about it (an `extra` package: that nothing is known), and the typed confirmation, journal, verification, rollback and restore are unchanged. This is how a new model gets tested.

*Owner decision 2026-10-23, optimizer profiles (R2, OPTIMIZER.md § 3):* the same "unknown devices get R0–R1 only" rule gates `rusttv optimize apply reduced-animations`: it is refused (`OPTIMIZE_NOT_TESTED`) unless the matching compat profile has `[[optimizer]] profile = "reduced-animations", version = <the profile's version>, tested = true`. For the first real-device test, a person may override this for one plan with `--allow-untested` (MCP `optimize_plan`: `allow_untested`, which only adds the flag to the command the person runs). Nothing else changes: the dry run says "UNTESTED on this model", and the typed confirmation (`optimize`), the other refusals (one optimizer journal at a time, an original value that doesn't validate, nothing to change), journal, verification, rollback and restore are the same. No profile is marked tested yet; the Philips 65OLED818 hasn't been measured.

If any chosen package fails rules 1–3, `extra` ones included, the whole plan is refused (`PACKAGE_PROTECTED`, naming each package and why). The checks run when the plan is made, and again inside `apply` right before each step, for that step's package (`Check::NotProtected`, added 2026-10-23): if a package became protected since planning (e.g. it now provides an enabled accessibility service), its step isn't run and the steps done so far are undone (`ROLLED_BACK`).

One exception, inside Home takeover only: a system package with a Home activity of higher priority than RustTV may be disabled (never uninstalled) when the device's tested profile lists it in `disable_home_packages`. On the Philips 65OLED818 that is the setup wizard, `com.google.android.tungsten.setupwraith` (owner decision 2026-10-23, D14): while it is disabled, its deferred-setup and reset screens are off too. Disabling only its Home activity would be narrower, but Android 14 doesn't let the adb shell change a single activity of a system app. See [Home takeover](#home-takeover-opt-in), rule 4.

## Approval on the TV

*Owner decision 2026-10-24 (HISTORY.md § 6).* The launcher's Settings page can approve **every** kind of change on the TV. What the launcher can do itself (its own state; the three animation scales once `WRITE_SECURE_SETTINGS` is granted) it applies there; the rest waits as a pending approval for the CLI ([The history door](#the-history-door)).

1. **What it proves.** The adb shell can inject key events that look exactly like the remote (it is in the `input` and `uhid` groups; `/dev/input/event*` and `/dev/uinput` are writable by them, measured on the Philips 65OLED818 on 2026-10-24), so a key press proves nothing. What adb can't do is see a window marked `FLAG_SECURE`. The confirmation therefore proves that someone **can see the TV**: it stops accidents and blind automation, agents included; a person looking at the TV with a remote is the person.
2. **The gesture.** The review screen lists every change (old → new; package ids shown, bidi controls and line breaks stripped from app labels) and sets `FLAG_SECURE` and hides other apps' overlays while it is open. Only after the person chooses **Approve** does it show a random 4-arrow code (`SecureRandom`), in a fixed left-to-right order in every language; then OK must be held for 2 s, timed from a fresh press at least 1 s after the screen opened. A wrong arrow closes the review; three wrong codes in a row lock TV approvals for 1 hour of TV uptime, doubling with each further lockout, kept across reboots. The OK that confirmed isn't passed on to the page below.
3. **Bound and recorded.** An approval binds to the SHA-256 of the exact change list and each changed value's old value; applying re-checks them live. On the TV, a journal is written before the first step, each step is verified by reading it back, and a failure is undone where the value is still what the step set; a change interrupted by a crash is finished or undone when the history next opens. History records the approval's hash.
4. **Test builds can't approve.** A debuggable or shell-profileable launcher (the shell could write its files with `run-as` or read its memory) shows the review as display-only, and the CLI refuses its pending approvals. `profileable` is only in builds made with `-Prusttv.profileable=true` for measurements.
5. **`WRITE_SECURE_SETTINGS` stays contained.** Only `SecureSettings.kt` writes a setting, for three keys by enum and the CLI's value rule. `android/check-dex.sh` (run by `build.sh` for every APK) fails the build on any other `Settings.*.put*` call, any `ContentResolver` write, or reflection in the launcher's classes; a Rust test keeps settings names out of the Rust code. Every `history sync` compares a watchlist of sensitive settings with a baseline on the computer.
6. **Agents** must never try to pass the code: it exists to keep them out. Reading the screen another way to defeat it (e.g. a camera) is the same breach as faking a terminal.

## Change lifecycle (R2–R3)

1. **Analyze** (read-only): collect device info and current state.
2. **Plan**: device fingerprint (`ro.build.fingerprint`), steps, risk class per step, and the original value for each step. The plan is stored inside its journal: one TOML file per change, no separate plan file.
3. **Dry-run**: render the plan as human-readable text with exact commands.
4. **Approve**: a human confirms in the CLI (typed confirmation for R3). MCP tools can create plans but not approve them. The CLI accepts the confirmation only when stdin is an interactive terminal, and has no `--yes` flag. The one exception is a [delegation](#delegated-approval) a human grants at a terminal. That proves a terminal, not a person: an agent driving a pseudo-terminal could type the word. Agents and MCP servers must therefore never be given a pseudo-terminal running `rusttv` (RISKS.md #15).
5. **Apply**: precondition check (same fingerprint, device reachable, protected-package check re-run). Write a journal entry *before* each step; run one step; verify its effect; stop on the first failure.
6. **Verify**: re-read state; confirm HOME still resolves to a launchable activity.
7. **Restore**: one journal-based restore per kind of change. It undoes, last first, every step the journal says may have run (started or done), verifies each undo, and keeps going past a failure, printing the manual command for it. A restore is never rolled back. If the device's fingerprint changed since the journal was written, restore warns and still runs: undoing is the safe direction, and a firmware update is a likely reason to restore. The commands are `rusttv launcher restore` (takeover journals) and `rusttv optimize restore [privacy|reduced-animations]` (privacy and optimizer journals; without a name it refuses when both kinds are restorable); each validator refuses the others' journals. *Optimizer restore:* a setting that is neither the value the plan set nor the one it found (someone changed it since) is left as is and named, never overwritten; this is checked when planning the restore and again right before each undo. A general `rusttv restore [--journal <file>]` on the same engine is still to come (OPTIMIZER.md decision 5).

Plans and journals live in a local state directory (`~/.local/state/rusttv/` on Linux, `~/Library/Application Support/rusttv/` on macOS, `RUSTTV_STATE_DIR` to override) and are plain text for auditability. The journal (TOML, `journals/<unix ms>-<plan>.toml`) holds the plan's steps, the original state checked before any step, and each step's progress. It is written atomically before the first step, when each step starts and ends, and at the end; if it can't be written, the change is rolled back. A journal is untrusted input when restoring: Home takeover and privacy restores refuse any step other than re-enabling a package, optimizer restores any step other than `settings put`/`delete` of an allowlisted key (keys and values are re-validated when the journal is read), and each only accepts journals of its own plan. A journal file that can't be read is never skipped silently: `launcher restore` warns about each one on stderr (suggesting `--journal <file>` or `--from-profile`), and uninstall and upgrade refuse while one is there (rule 6). *Owner decision 2026-10-23:* `optimize apply reduced-animations` refuses the same way (`PRECONDITION_FAILED` naming each unreadable file and why), because the file may be an unrestored optimizer journal and a second plan would record the first plan's values as originals: check it, restore it if needed (`rusttv optimize restore --journal <file>` after fixing it), then move it out of the journal directory.

## Recovery scenarios

| Scenario | Design response | Residual risk |
|---|---|---|
| RustTV launcher crashes on boot | Without Home takeover the stock launcher still owns Home. With it: `rusttv launcher restore` (re-enables the stock launcher over ADB); manual path documented for Settings → Apps → System apps → enable | Some firmware may loop; user can still uninstall via ADB |
| ADB connection lost mid-apply | Journal shows the last completed step; `restore` resumes when reconnected | If Wi-Fi ADB is disabled by a reset, USB or manual settings needed |
| Device reboots mid-apply | Same as above; R2/R3 states persist predictably | — |
| Firmware update re-enables/changes packages | `optimize analyze` detects fingerprint change and marks plan stale | Behavior of new firmware is unknown until tested |
| Network ADB unavailable | All TV-side functionality (launcher) works without it | — |
| Restore fails | Print exact manual commands and Settings paths per step | **Recovery is never guaranteed**; we say so in docs and CLI output |

## Home takeover (opt-in)

*Owner decision 2026-10-23 (ARCHITECTURE D12).* On Google TV the stock launcher declares a higher HOME priority than any third-party app can (RESEARCH §8), so RustTV can only become the Home screen if the stock launcher is disabled. This is the **only** permitted change to the stock launcher, and it is R3 with these extra rules:

1. **Opt-in only.** Never part of an optimization profile, never suggested by default; a separate command (`rusttv launcher takeover`) with typed confirmation. MCP cannot request it.
2. **Known devices only.** Offered only when the device's compat profile names its stock launcher package and records a successful takeover and restore on that firmware family. *As built:* profiles from `compat/devices/` are compiled into the binary (so dropping a file somewhere can't satisfy the gate); one must match manufacturer, model and codename, and the firmware family (fingerprint without build ID and incremental: same Android version and build type), and its `[launcher]` section must name the package Home opens and set `takeover_tested = true`. Otherwise `TAKEOVER_NOT_TESTED`. Emulator profiles are never marked tested. The first takeover on a new device therefore needs a development build with that profile edited locally; commit `takeover_tested = true` only after takeover **and** restore succeeded on it.
3. **Preconditions.** RustTV launcher installed, launchable, and verified drawing frames; ADB connected; the stock launcher package is the current HOME resolver. *As built:* before the change, RustTV must be a HOME candidate and the HOME resolver must be a system app that outranks RustTV's priority. "Launchable and drawing frames" is checked after the change, as part of rule 5 (resumed activity with a live process); frame drawing itself isn't measured.
4. **Disable, never uninstall.** `pm disable-user --user 0 <stock launcher>` only; original state recorded in the journal first. *As built:* Android opens the highest-priority Home activity without asking and ignores the preferred Home (the Home role) when one outranks the rest, so every other system activity above RustTV's priority would win Home once the stock launcher is gone. Each one's package must be listed in the profile's `disable_home_packages`, or the plan is refused with `TAKEOVER_NOT_TESTED`; the plan disables those packages first (`pm disable-user --user 0`), while the stock launcher still wins Home, then the stock launcher. Restore re-enables them last.
5. **Verify or roll back automatically.** After disabling, HOME must resolve to RustTV and RustTV must come to the foreground on a HOME key event within a timeout; otherwise re-enable the stock launcher immediately. *As built:* `input keyevent KEYCODE_WAKEUP` (R1) and up to 5 s for `dumpsys power` to report `mWakefulness=Awake` (a screensaver swallows the HOME press: it only ends the screensaver, seen on the Philips 65OLED818 on 2026-10-24) and for `dumpsys window windows` to show an app's activity with input focus, not a system overlay (the Philips logo overlay takes focus while the TV is awake, also seen that day; RustTV doesn't press a key to dismiss it, since that key would also reach whatever app is open: the plan rolls back before pressing HOME and asks the person to press any key on the remote and run it again), then `input keyevent KEYCODE_HOME` (R1), then for up to 10 s the resumed activity (`dumpsys activity activities`) must be `ai.rusttv.launcher` and its process must be in `ps`.
6. **Restore is one command.** `rusttv launcher restore` re-enables the stock launcher; RustTV is never removed while the stock launcher is disabled, so the TV is never left with only Android's fallback Home. *As built:* `rusttv launcher uninstall` (and an upgrade by `launcher install`) refuses, with `PRECONDITION_FAILED` telling the person to run `rusttv launcher restore` first, when a takeover journal for this firmware isn't restored, when a `.toml` file in the journal directory can't be read (it may be an unrestored takeover; the error names each file, and the person checks it, restores if needed, then moves it out of the directory), or when no system launcher other than RustTV can handle Home (catches a takeover from another computer or by hand). It doesn't restore inside the same plan: the restore then runs through its own verified plan and marks the takeover journal restored, and the uninstall journal never contains a step whose undo would disable the stock launcher again after RustTV is gone. After uninstalling, Home must open the stock launcher.
7. **Documented manual recovery** in the user docs, for when ADB is unavailable (Settings → Apps → show system apps → enable). Re-enabling the stock launcher there brings the stock Home back even with the other disabled packages still off (it outranks them); enable those the same way, or with `rusttv launcher restore`.

Restore without a journal (journal lost, or the takeover ran from another computer): `rusttv launcher restore --from-profile` rebuilds the takeover's journal from the device's compiled-in profile, which, unlike a journal file, is trusted. It lists only the packages that profile's takeover disables (`disable_home_packages`, then the stock launcher) that are disabled on the device now, and restores them through the same never-rolled-back restore. A device without a matching profile gets `NO_JOURNAL` and the Settings path. The takeover plan also shows the undo commands and the Settings path, and a failed undo prints its command again.

Residual risk: firmware updates may re-enable the stock launcher or change its package; `optimize analyze` must detect and report this. Recovery is never guaranteed.

## AI agents

- Agent output is untrusted input. MCP tools validate arguments against schemas and the protected-package policy, exactly like CLI input.
- No MCP tool accepts commands, shell strings, or arbitrary package lists for R3.
- MCP can read, analyze, and propose plans; approval is a separate human CLI step. *As built:* the MCP plan tools (`launcher_install_plan`, `launcher_uninstall_plan`, `launcher_restore_plan`, `privacy_plan`, `optimize_plan`, `optimize_restore_plan`) return the dry run and the `rusttv` command a person runs at a terminal; they run only R0 commands and write no journal. There is no MCP tool to plan a Home takeover, or to approve or apply anything (MCP.md).
- Typed confirmation proves only an interactive terminal. Never give an agent or MCP server a pseudo-terminal that runs `rusttv` (see Change lifecycle, step 4).
- Agents and MCP servers must never create or edit the delegation file (`approval-grant.toml`), nor run `rusttv approve` (see [Delegated approval](#delegated-approval)). MCP is unchanged by delegation: its tools stay dry-run only.

## Delegated approval

*Owner decision 2026-10-24.* Typing three confirmations (restore, install, takeover) for every launcher update is too much, and the owner wants an agent to be able to install the launcher during a session. A plain `--yes` flag was rejected. Instead:

1. **`rusttv launcher upgrade`.** Without an active Home takeover it is `launcher install` with the confirmation `upgrade`. With one, it runs `launcher restore`, `launcher install` (upgrade) and `launcher takeover` as three separate existing plans, in that order, each with its own journal, rollback and verification, unchanged: the engine's rule that an irreversible step is a plan's last still holds, and the plans are never merged. Each later plan is made when its stage starts, against the device's real state then, so one confirmation can't bind the exact later plans. After a person types `upgrade` at a terminal, an in-memory grant for this serial, firmware fingerprint and the launcher scope, alive only for this process, approves each stage's plan (`Grant::for_this_run`; journals record `approved_by = { by = "upgrade" }`). The dry run and the prompt show the restore plan in full and say what follows. It stops at the first stage that fails and says how the TV is left and what to run; the order (restore before install, takeover last) never leaves the TV without a working Home: if the install fails, the stock launcher is Home with the old RustTV; if the takeover rolls back, the stock launcher is Home with the new RustTV.
2. **Time-limited delegation.** `rusttv approve --for <duration> --only launcher [--serial <s>]` needs an interactive terminal and the typed word `delegate`, after showing the device (serial, model, fingerprint), the scope and the expiry. It writes `<state dir>/approval-grant.toml` (one at a time; at most 2 h, default 30 min); `--status` shows it, `--revoke` deletes it. While it is valid, a plan-applying command run **without** a terminal is approved by it if the grant's serial and fingerprint are the plan's (the apply re-checks the fingerprint on the device) and its scope covers the plan; stderr notes the delegation. With a terminal the command asks as usual. Scope `launcher` covers exactly the `launcher-install` plan (`launcher install`, `launcher upgrade`, `update launcher`), `home-takeover` and `home-takeover-restore`; never `launcher uninstall`, `optimize` or `update cli`. Scopes are an enum, so more can be added by a later owner decision. The core API is a separate constructor, `Plan::approve_by_grant`, next to `Plan::approve`; an `Approval` is still valid for its one plan only. Journals record `approved_by` (`terminal`, `delegation` with the grant's `granted_at_unix_ms`, or `upgrade`).
3. **What it rests on.** The grant file is policy, not cryptography: on a machine where an agent can write files, it could write the grant itself. So, with the same strength as the rule never to give an agent a pseudo-terminal running `rusttv`: agents and MCP servers must never create, edit or copy the grant file, nor run `rusttv approve`. Only the CLI calls `Plan::approve_by_grant`, and only with a grant a person created at a terminal. A grant file that doesn't parse or claims more than 2 h approves nothing. MCP is unchanged: its tools stay dry-run only and create no approval.

## Updates

`rusttv update` (CLI.md § Updates, ARCHITECTURE D17) installs RustTV releases: the CLI on this computer and the launcher on a TV.

- **Trust root:** the owner's minisign update signing key, whose public half is compiled into `rusttv` (`RELEASE_SIGNING_KEY`; RELEASE.md § Update signing key). `SHA256SUMS` must carry a valid signature by it, and each file's size and SHA-256 must match, before anything is installed or replaced. GitHub, TLS and the release feed only say which version is newest. Until the key is set, the install and replace paths refuse (`UPDATE_VERIFY_FAILED`). Both signing keys are secrets of the protected GitHub environment `release` (owner decision 2026-10-25): only the Release sign workflow on `main` can read them, only after the owner approves the run, and admins can't bypass that; the job that holds them runs no repository code and no third-party action. GitHub Actions builds the release files from the tagged commit; Release sign first checks, without the keys, that every file comes from the tag's Release build run (the run's own `SHA256SUMS`, which can't change after upload), then signs them; the owner publishes (RELEASE.md). `main` changes only through pull requests with green CI, and `v*` tags can't be moved or deleted. A signature therefore says the owner approved those files, not that the build was reproduced; someone who controls the build could slip in a bad binary that the owner then approves. Keeping the keys on GitHub also makes the owner's GitHub account part of the trust root: whoever controls it can approve a signing run. The originals stay offline with the owner.
- **Launcher:** additionally, Android installs an upgrade only if it is signed with the installed launcher's APK key, and the normal `launcher install` plan runs unchanged (dry run, typed confirmation, verify, journal).
- **CLI:** the old files are kept as `.previous` and put back if the new `rusttv --version` doesn't report the release's version. Typed confirmation `update`, same terminal rule as device changes.
- **No downgrade:** only a strictly newer `v<major>.<minor>.<patch>` release; drafts and pre-releases never count. File names carry the version, so a validly signed older `SHA256SUMS` can't pass for a newer release.
- The production key can't be replaced at run time: only debug builds with the `test-util` feature (the CLI's own tests) read a test key from `RUSTTV_UPDATE_TEST_KEY`; release builds have no such code.
- Downloads: `curl` with a fixed argument list (no shell), HTTPS only (also redirects), TLS 1.2+, a size cap; URLs only on `github.com` / `objects.githubusercontent.com`. Not exposed through MCP.

## Launcher updates

*Owner decision 2026-10-24 (PROJECT_VISION.md, ARCHITECTURE.md D18).* The launcher checks for a newer version of itself and can install it on the TV. This is on by default, and there is no off switch until the launcher has a settings page. It runs on the TV at the user's request, without ADB, so it is outside the CLI's safety engine and risk classes; it can only replace `ai.rusttv.launcher` with a newer build signed by the same key, and touches no other package or setting.

- **Network: GitHub only.** The launcher holds `INTERNET` for this alone (`Updater.kt`). It fetches `https://api.github.com/repos/damienmiheev/rusttv/releases/latest` (a few KB of JSON, capped at 1 MB) on resume when the last successful check is over 24 hours old (a failed one is retried on resume after an hour), and when the user presses OK on the About page with no update known. Only when the user presses OK to install does it download that release's `SHA256SUMS` (capped at 64 KB) and the APK for the TV's ABI. Every request and every redirect hop must be https on port 443 to `api.github.com`, `github.com`, `objects.githubusercontent.com` or `release-assets.githubusercontent.com` (where GitHub redirects release downloads); anything else is refused. Requests carry `User-Agent: RustTV-Launcher` and no identifiers, cookies or tokens. GitHub sees the TV's IP address and the time, as with any download; nothing about the TV or its apps is sent.
- **What counts as an update.** Not a draft or pre-release; tag exactly `v<major>.<minor>.<patch>`; a versionCode (`major * 10000 + minor * 100 + patch`, RELEASE.md) strictly greater than the installed app's. Never a downgrade: the downloaded APK's own versionCode is checked again.
- **Checks before Android sees the APK.** The asset is `rusttv-launcher-<version>-<abi>.apk` for the first of the device's ABIs that the release has; its size is at most 64 MB and the download must be exactly that size; its SHA-256 must equal its line in `SHA256SUMS`; the archive's package must be `ai.rusttv.launcher`, its versionCode newer than the installed one, and its signing certificates equal to the installed app's (`PackageManager.getPackageArchiveInfo`). The APK is written to the app's cache directory and deleted once it is copied into the install session, or when a step fails.
- **Trust root: Android's same-key rule.** Android installs an update only if it is signed with the installed app's key, the release key (RELEASE.md § Signing), which only the approved Release sign job can use (§ Updates above): the owner's GitHub account and approval guard it. The TV does not verify `SHA256SUMS.minisig`: `SHA256SUMS` comes from the same release as the APK, so its hash and the size check catch corruption and mix-ups but add no trust, and a minisign check would add a second key whose loss only matters once the release key is lost too, at the cost of a pinned key and a verifier on the TV. So someone who controls the GitHub release or the connection can at worst withhold updates or offer an APK that the checks or Android refuse. Someone with the release key can offer an update to every TV with the check on; the user still has to confirm it. A launcher built with another key (debug builds, CI artifacts) refuses release updates ("not signed with RustTV's key").
- **The user confirms every install.** RustTV is not a system or device-owner app: it opens a `PackageInstaller` session and Android shows its own confirmation. The first time, the launcher opens Android's "Install unknown apps" screen for RustTV and says so on the About page. The session's result receiver is not exported, so only the system installer's reply to RustTV's own PendingIntent reaches it.
- **With Home takeover.** An update restarts the launcher like any app update. If a new version fails to start while the stock launcher is disabled, recover with `rusttv launcher restore` ([Recovery scenarios](#recovery-scenarios)).

## RustTV Remote (phone)

*Owner decisions 2026-10-25 (REMOTE.md, ARCHITECTURE.md D24).* A TV-side feature like launcher updates, outside the CLI's risk classes. Planned for 0.3.0; nothing is built yet.

- **Threat model.** An attacker on the home network: a guest who knows the Wi-Fi password (on WPA2 they can decrypt other clients' traffic after seeing their handshake), a rogue access point, or a compromised device. Plain HTTP gives no server identity, so the design assumes the network is hostile:
  - the long-term secret never crosses the network after pairing (HMAC challenge-response);
  - every message after authentication is XChaCha20-Poly1305 with a direction byte and a counter, so typed text and keys can't be read or replayed;
  - the pairing secret is in the QR code's URL fragment, which browsers never send, valid 2 minutes, one use, only while the pairing screen is open; the TV and the phone show the same 2-digit code and the person presses OK on the TV remote.
- **What a paired phone can do:** what a remote can do — keys, text, open an app, edit Home's order and folders, and pointer taps in listed apps. **It can never** change a setting or a package, pair or revoke phones, write to the history store, or pass the review screen: the review/approval screen drops all phone input (it arrives through RustTV's own socket, so it is told apart from the remote).
- **What only the person does on the TV:** pair or revoke a phone, connect RustTV to the TV's Remote Service, list apps for the pointer. Each is a Settings action with a preview, OK, and a `tv` history entry.
- **The listener** runs only while a phone is paired, refuses anything unpaired after one small header, and caps every length, connection and message rate (REMOTE.md § 3). A parser panic would kill Home, so the parser has property tests and a fuzz run.
- **Secrets on the TV** are in the launcher's private storage (`files/remote/phones.toml`); a damaged file means "no phones". Debuggable builds refuse to pair. On the phone they are in the page's `localStorage`; clearing site data unpairs it.
- **The Remote Service pairing** gives RustTV a credential that can press any key in any app and type into any field, the same power as the Google TV phone app. Only a typed key enum reaches it. Removing the pairing deletes RustTV's key and the pinned certificate.
- **The pointer's accessibility service** is declared with `canPerformGestures` only: no window content, no key filtering, only the package name from window changes, so it can't read what other apps show or what keys are pressed. It acts only while a listed app is in front, is off by default, and is turned on by the person in Android's settings (`history sync` warns once when `enabled_accessibility_services` changes). `check-dex.sh` keeps the accessibility APIs in `PointerService.kt` only.

## ADB hygiene (user guidance)

- Legacy Wi-Fi ADB (TCP 5555) relies only on the one-time RSA key approval and is unencrypted; enable it only on trusted networks and disable it after use.
- Prefer `adb pair` (API 30+) where available.
- Revoke USB debugging authorizations when finished.

## Supply chain

- `cargo deny check` in CI: RustSec advisories, license allowlist (permissive + MPL + Slint's royalty-free license, D9), banned/duplicate crates. Ignored advisories need a reason in `deny.toml`; so far only unmaintained crates used by the desktop dev mode, never by the APK.
- `Cargo.lock` committed; dependencies pinned; Slint pinned with `=`.
- Skia (linked by Slint's Android renderer) is a prebuilt binary per ABI that `android/build.sh` fetches and checks against a pinned SHA-256. arm64-v8a and x86_64 come from rust-skia's skia-binaries releases. rust-skia has no armeabi-v7a build, so ours is built from source by the manual workflow `.github/workflows/skia-armv7.yml` ([run 39956273511](https://github.com/damienmiheev/rusttv/actions/runs/39956273511)) and hosted as the release `skia-0.153.3-armv7` of this repository. It must be rebuilt, re-released and re-pinned whenever Slint (and so skia-bindings) is upgraded.
- Release APKs signed with a project key; checksums published with each release and signed with a separate minisign key. Both keys are used only by the owner-approved Release sign job (§ Updates). Every release file also has a Sigstore-signed GitHub build provenance attestation, made by a job that holds no keys and runs no repository code, and each binary has a CycloneDX SBOM (RELEASE.md). These help people audit a release; they are not part of the update trust root. Reproducible builds investigated in Phase 6.
- No running of unvetted third-party tools (see RESEARCH.md §4).
